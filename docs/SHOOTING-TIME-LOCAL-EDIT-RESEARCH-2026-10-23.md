# 拍摄时间局部修改方案研究

日期：2026-10-23。状态：研究与隔离原型验证完成，未接入业务代码、未替换本地应用。

## 结论

**技术可行，值得优先优化大视频；不能直接把所有格式改成同一种原地写入。** 对普通 MOV/MP4 已存在且位置、长度明确的时间字段，可以只改几十字节，避开复制整段视频。真正需要解决的是日期字段一致性、格式识别、失败后的状态核对，以及移动硬盘的写入安全。

建议采用“按结构识别的局部写入 + 明确的兼容处理”。先覆盖验证过的普通 MP4/MOV；尼康专有日期单独适配；照片、RAW、HIF、MTS 等分别评估。不满足条件的文件不应静默进入整文件重写，更不能报告为已成功。

本研究只读统计生产库、读取少量原片元数据。所有写入均作用于独立临时目录的合成文件；没有修改真实素材、数据库记录、模型、现有备份或已安装应用。

## 当前为什么慢

当前实现位于 [library.py](/Users/zack/program/python/video_analyzer/backend/blueprints/library.py:1415)：50 文件一批，调用 ExifTool，对 `DateTimeOriginal`、`CreateDate`、`TrackCreateDate`、`MediaCreateDate` 做相同小时偏移，再偏移数据库中的 `date_taken`。

`-overwrite_original` 会生成修改后的临时文件，再替换原件。减少子进程启动次数不能消除整段视频的读写。ExifTool 官方也明确说明：固定长度字段理论上能局部修改，但它没有提供这种通用写入路径。[ExifTool FAQ 31](https://exiftool.sourceforge.net/faq.html#Q31)

`-overwrite_original_in_place` 也不是局部字段写入：它会把临时文件的内容再复制回原文件，主要用于保留文件属性，还增加一次复制。不能靠换这个参数提速。[ExifTool 参数文档](https://exiftool.sourceforge.net/exiftool_pod.html#overwrite_original_in_place)

项目旧设计文档把“改嵌入元数据需重写整个 MP4”描述成了格式限制。准确说法应是**当前 ExifTool 写入路径会重写**；固定长度、同位置的修改并非必然如此。

## 本机收益范围

只读查询现有资料库得到：

| 格式 | 数量 | 库记录对应容量（十进制） |
| --- | ---: | ---: |
| MP4 | 1,311 | 1.007 TB |
| MOV | 433 | 242.3 GB |
| NEF | 2,677 | 134.9 GB |
| JPG/JPEG | 4,314 | 50.8 GB |
| TIFF | 67 | 44.5 GB |
| HIF | 1,857 | 10.4 GB |
| DNG | 127 | 7.7 GB |

MOV/MP4 合计 **1,744 个、1.249 TB，占照片与视频总记录容量的 83.4%**。这是潜在优化对象，**不是已确认能走快速路径的数量**。相机记录以 DJI 系列 MP4 和 Nikon Z 8 MOV 为主。库记录容量不等于本次测量了这些源文件的读写速度。

读取最多 8 个在线视频的日期字段：1 个普通 MP4、1 个 DJI MP4、6 个 Nikon MOV。它们均有版本 0 的标准时间头；DJI 样本有 5 条轨道，尼康样本还含专有日期。这个非随机小样本不足以代表整个库。

两块已挂载素材卷均为 **USB / exFAT**。本机 APFS 上的测试结果不能直接当作移动盘成绩；也不能假定能在这两块盘上使用 APFS 克隆备份。

## 原型实际验证

标准头部的 `mvhd`、每条轨道的 `tkhd` 与 `mdhd` 中，创建时间可以是 4 字节或 8 字节整数。研究原型解析容器边界并定位这些字段，只改变原位置的时间值，不改变容器大小、媒体偏移和媒体时间轴。字段与版本定义同时核对了本机 ExifTool 13.55 的 `QuickTime.pm`。[QuickTime 字段文档](https://exiftool.sourceforge.net/TagNames/QuickTime.html)

已验证：

- 4 组可解码合成音视频：MP4、MOV、前置头部 MP4、版本 1 的 MOV；分别偏移 +8、-24、+24、-8 小时。
- 普通双轨视频只写 5 个字段，共 **20 字节**；版本 1 共 40 字节。前后文件长度、inode 相同，其他所有字节不变；`mdat` SHA-256 和音视频解码散列一致，ExifTool 读回正确。
- 零值未知日期、越界、下溢、未知头版本、分片容器、截断结构：6 组均在写入前拒绝，文件散列不变。这是原型的保守边界，不意味着这些格式永远不能支持。
- 20 字节是写入 API 的数据量。磁盘实际仍按页或扇区执行写入，不能解释成物理设备只写 20 字节。

为观察体积影响，在合成视频后附加 64 MiB / 512 MiB 的稀疏 `mdat`，三轮取中位数：

| 操作 | 附加 64 MiB | 附加 512 MiB |
| --- | ---: | ---: |
| 当前 ExifTool 命令 | 181 ms | 467 ms |
| ExifTool `in_place` 参数 | 215 ms | 793 ms |
| 仅定位、写入、fsync 与字节读回 | 0.21 ms | 0.54 ms |

另一个 512 MiB 合成用例加入写前日志、目录同步和 macOS `F_FULLFSYNC`，中位约 **10.1 ms**。模拟写完 2 个字段后中断，重新打开能识别为“2 个新值、3 个旧值”，没有自动恢复或重做写入。

**这些数据只证明机制差异，不是产品端到端速度承诺。** 环境是本机 APFS SSD；大部分附加内容是稀疏零数据，且校验读取会影响缓存。快速原型计时不含 ExifTool 进程读回、数据库提交、任务协调或真实 USB 刷盘延迟；日志原型也未覆盖这些环节。尚未做移动硬盘写入、断电或拔盘测试。Apple 对强持久化需求建议使用 `F_FULLFSYNC`，但这仍不等于已经验证具体 USB 硬件的断电行为。[Apple 磁盘写入说明](https://developer.apple.com/documentation/xcode/reducing-disk-writes)

## 不能只修改标准头部

### 多处日期的一致性

合成测试同时放入 QuickTime、XMP、Apple `Keys:CreationDate`：只修改标准头后，XMP 与 Apple 日期都保持旧值。当前业务的四字段 ExifTool 命令也不会偏移 `Keys:CreationDate`。因此，需要先枚举日期及其来源，确定拍摄时间语义，再决定能否全部以相同长度修改。

时区不能一律按北京时间或 UTC 重解释。对“整体移动 N 小时”，应保留各字段原有的时区表达，调整相应数值；不能把没有时区的相机时间擅自变成 UTC。媒体播放时间戳、帧间隔和音画同步不属于此次调整范围。

### Nikon Z 8 是实际相关的特殊情况

6 个只读 Nikon 样本均同时存在 `Nikon:DateTimeOriginal`、`Nikon:CreateDate`。ExifTool 将 Nikon NCTG 中这两个字段标为只读。[Nikon NCTG 文档](https://exiftool.sourceforge.net/TagNames/Nikon.html#NCTG)

另用完全合成、无私人信息的 Nikon NCTG 记录复现：当前业务命令让标准时间从 03:04 改成 11:04，但 Nikon 两个字段仍为 03:04。按当前 [导入字段优先级](/Users/zack/program/python/video_analyzer/backend/services/importer.py:409) 重新读取，选中的 `DateTimeOriginal` 仍为旧日期。这是合成复现；没有在原片上写入，也不能认定现有 433 个 MOV 都已经发生过此问题。

尼康方案应单独验证其记录位置、格式、长度和关联字段。未完成验证前，应明确显示不支持完整同步，不能只改标准头后声称“拍摄时间已全部调整”。其余厂商的私有或逐帧元数据也需要同样的识别边界。

### 结果判定也需要同步设计

静态核对发现，当前 [_run_exiftool_chunk](/Users/zack/program/python/video_analyzer/backend/blueprints/library.py:1244) 只匹配 stderr 中带文件路径的 `Error:`，没有逐文件读取目标日期；不在失败集合中的文件都会推动数据库偏移。整批超时则全批算失败，无法表达“前面的文件已经写完”。因此，新路径不能沿用这种成功判定，也不能在超时后对整批自动重试相对偏移。这些是当前控制流的边界分析，本轮未在生产任务中制造超时或故障。

## 现成工具比较

| 路线 | 判断 |
| --- | --- |
| 继续 ExifTool，增加并发 | 能降低部分启动成本；大量同盘视频仍整文件读写，机械盘并发还可能增加寻道。不解决主问题。 |
| ExifTool `-fast` / `-fast2` | 针对读取范围的取舍，不能把元数据写入变成局部写入；不能为快而漏掉所需字段。 |
| FFmpeg `-c copy` | 不重新编码，但仍将媒体包写入输出容器，不是几十字节的修改；还需核对私有元数据保留情况。[FFmpeg streamcopy](https://ffmpeg.org/ffmpeg.html#Streamcopy) |
| GPAC MP4Box | 成熟候选：官方支持有条件的 in-place 编辑，也有电影/轨道/媒体创建时间选项。但可能移动文件内媒体数据，速度取决于布局；官方明确警告中断可能损坏文件。需要验证实际是否只改目标区域，不能直接替换现有命令。[in-place 说明](https://wiki.gpac.io/Howtos/mp4box-inplace/)、[时间参数](https://wiki.gpac.io/MP4Box/mp4box-gen-opts/) |
| Bento4 `mp4edit` | 支持替换 atom，官方 CLI 接口是输入/输出文件；不能据此推断为原位置字段修改。[Bento4 文档](https://www.bento4.com/documentation/mp4edit/) |
| JCodec | 提供原位电影头部编辑；值得参考其边界处理，但引入 JVM 不契合当前 Python/Electron 运行环境，本次没有运行验证。[JCodec 文档](https://www.jcodec.org/docs/working_with_mp4_metadata.html) |
| 受限的固定字段写入器 | 与现有技术栈最容易集成，能明确保证不移动媒体区；维护责任集中在解析边界、字段同步与恢复协议。原型已验证核心机制，尚非可交付功能。 |
| 仅保存资料库或 XMP 侧车 | 原片不写入，速度与恢复最容易控制；外部软件是否采用取决于其兼容性。适合另行提供选择，不能静默代替“修改原文件拍摄时间”。 |

GPAC、Bento4、JCodec 本轮仅核对官方文档，没有安装或做本机性能对照；暂不能断言受限写入器优于所有成熟库。

## 建议的接入约束

1. **先检测，再制定整份写入计划。** 校验真实格式、box 边界、版本、所有轨道、日期来源与整数范围。只替换已存在、长度不变且已适配的字段；不移动 `mdat`，不扩展头部，不新增日期。
2. **写入前持久保存恢复依据。** 包含操作 ID、文件身份、目标偏移、原始字节与绝对目标字节，以及原始时间属性。日志失败则不写原片。小日志不能代替完整素材备份，也不能提供拔盘零风险保证。
3. **按文件协调任务。** 避免本应用导入、刷新、另一次时间修改同时处理同一文件；写前复核文件身份与旧字节，处理短写、离线和身份变化。同一物理盘先从单写入任务验证，不追求高并发。
4. **核验成功后再更新资料库。** 先持久化并读回所有目标字节，再按统一拍摄时间规则重新读取元数据。数据库以实际结果为准；同步处理 `file_mtime`，不能只把旧 `date_taken` 加 N 小时就当作成功。需明确是否保留系统修改时间，并保持导入变更检测一致。
5. **中断时保留现场。** 相对偏移必须转换为这次操作的绝对目标，防止重试又偏移一次。未知/混合状态应停止同卷后续写入，保留日志，展示部分完成情况；不自动回滚、恢复原件或盲目重跑。
6. **兼容路径有明确边界。** 未知结构、需改变长度、分片、受保护/签名文件、私有日期未适配等先拒绝快速路径；让用户在明确预计耗时后选择兼容写入，或仅保存库内修正。兼容工具本身也须先证明能同步所需字段，不能把 ExifTool 当作所有格式的兜底保证。

支持克隆的同卷 APFS 可以进一步评估“克隆工作副本 → 局部修改 → 校验后替换”，或保留克隆原件。克隆的后续写入相互隔离；调用要求受支持的同一文件系统。它不适用于当前两块 exFAT 素材卷，也不代替独立备份。[Apple clonefile 定义](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/clonefile.2)

照片可以作为后续独立阶段：JPEG/TIFF 中已存在的定长 EXIF 时间有类似机会；RAW 涉及厂商目录、MakerNotes 和完整性字段，HEIF/HIF/CR3 虽也可能采用 box 容器，内部元数据定位与视频不同。本轮没有验证这些格式的局部写入，不承诺全格式支持。

## 下一步验收范围

推荐先做普通 MP4/MOV 的保守快速路径，同时把 Nikon 日期适配作为明确的兼容任务。上线前至少验证 DJI、Nikon、手机视频的安全测试副本，以及前后置头部、多轨、4/8 字节日期、时区/夏令时、零值和跨年；再做 exFAT 上的合成写入、进程中断、权限/磁盘满/离线及数据库提交失败测试。原片备份和受控写入验证完成之前，不应批量作用于现有素材。

通过标准应是：目标日期读回一致、媒体字节与解码结果相同、其他关键元数据保留、失败不误报、不重复偏移、重新导入不恢复旧日期、任务与恢复状态明确。完整散列/解码用于验收；正式处理若每次扫描整个视频校验，又会重新引入按体积增长的读取成本，应采用经过验证的定点核验策略。
