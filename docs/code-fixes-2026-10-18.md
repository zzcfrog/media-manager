## 接口与数据行为

- `PUT /api/workbench/<id>/tracks` 新增可选 `plan` 对象，与 `tracks` 一起提交；旧请求仍支持只存轨道。客户端把轨道和方案捕获为同一份快照，排队保存，撤销/重做也走同一路径。此队列解决当前页面的乱序写入，未增加跨窗口/跨客户端冲突合并协议。
- `POST /api/creative/<id>/apply` 可在 JSON 中携带 `plan`；方案和生成的轨道同事务落库，失败回滚。无请求体时继续使用数据库中的方案。
- 工程镜头可携带 `shot_id` 和 `source` 来源快照，快照包含媒体 ID、原始时间范围和分析信息。时间范围完全相同的重新分析复用片段 ID；范围改变时，工程继续使用其原来的剪辑范围。没有新增数据库列，也没有重排现有数据库字段。
- 同步变更文件保留已有标注与分析。若实际替换了源文件内容，旧分析仍需用户主动重新分析以反映新内容；本次没有对真实库自动重分析，也没有修复历史已丢失的数据。
- 非原生视频首次播放需要等待完整预览转码；生成文件位于数据目录的 `preview-cache`，普通缓存保留量约 2 GiB，单个正在使用的大预览可超过此值。原生视频仍直接播放。缓存只存派生预览，不改源素材。
- 部分离线的导出明确提示跳过数量，并在 ZIP 中保留完整警告；全部离线时拒绝导出空视频时间线。
